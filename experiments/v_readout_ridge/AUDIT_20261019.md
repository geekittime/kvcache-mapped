## 3. 数学与实现

共同部分为 28 层同层映射、head mixing、分开 K/V、pre-k-norm/pre-RoPE、无 bias。只引入 NVIDIA 的 λ=0.01 ridge 项，没有引入该论文的 affine/centering、跨层选择或 FineWeb 校准集。两组 K 使用同一拟合解并逐字节比较。

weighted 的 token 权重是 continuation 所有 query 和所有 query heads 的 attention 均值。readout 针对每个目标 KV head，保留对应两个 query heads 的独立 attention 行，先算 AX、AY，再求 Gram/cross；不会先平均 attention 再计算 Gram。所有 source V heads 均可作为特征。统计和求解 FP64，保存 FP32；teacher BF16，softmax FP32。正则化加到 corpus-sum Gram 的对角线，用 Cholesky 求解，不显式求逆。

readout 每个 KV head 使用 1/(Gm) 归一化，保持每个样本的权重不随 continuation 长度增加；weighted 使用全 query/head 均值。λ 是相同数值，但两个设计矩阵的谱与尺度不同，**不能解释为两组具有完全相同的有效正则化强度**。这也是报告必须注明归一化的原因。

prefix-only softmax 是对论文 Eq.3.4 的字面实现；不声称已由作者源码验证。真实生成的 attention 还包括 continuation keys，且 mapped K 改变 query/attention，因此该 readout loss 是固定 native teacher attention 下的代理目标，不是端到端生成损失的精确闭式最小化。

**KV-Lingo weighted loss 本身不是数学错误。** 对非负且和为 1 的 attention，Jensen 不等式给出 `||Σ a_i e_i||² ≤ Σ a_i ||e_i||²`；它是较保守的上界。readout 保留交叉项，也可能允许误差抵消。更小的训练 readout loss 不保证更好的 held-out KL 或任务准确率。

此外，此比较不只是在同一个矩阵上“加上非对角项”：readout 的对角项为 a_i²，weighted 为 a_i，而且本地 baseline 全 head 平均，readout 区分目标 KV head。结果应称为两个完整 V 目标的对照，不能单独把增益归因于交叉项。若后续要分解原因，需要另设诊断对照，不能在看到测试分数后改变本轮定义。

## 4. 缓存注入和预测位置

已有真实模型检查覆盖两个模型的 identity cache、split logits、不同长度左 padding，以及约 16k prefix 的所有 28 层 teacher attention/readout capture。目标 key norm、RoPE 只应用一次；源 prefix 翻译到最后一个模板 token 之前，最后一个模板 token 由目标模型原生处理。

本轮新增 tiny Qwen3 因果性检查：在相同 prefix 后加入 continuation 不会改变 prefix K/V；并检查捕获的 query、prefix key 范围。此前新增的 decoder 检查把 131-token teacher forcing 与整段 forward 对比，覆盖 64/128 两个 chunk 边界，避免 off-by-one。

真实 32k RULER、batch=4 的两方向注入已通过，但只用 smoke mapper 和 16-token 生成上限；这是容量/执行检查，不是 2,048-token 正式评测已经通过。

## 7. 正式评测阶段发现的解码差异（历史处理，已由第 8 节取代）

完整拟合现已完成：两个方向各 400 条，保存的 FP32 maps 与 moment shards 都通过独立审计。两方向各 64 条 held-out 验证也均通过（日志和 JSON 位于 `checks/independent_fit_*`、`checks/validation_*_full`）。之后四个 ARC-C off full 数据集均完成逐样本评分审计，得分分别已写入各自 `runs/*/*/arc_off/full/results.json`；但首轮协调器因一个不合理的 smoke 条件停止。

具体情况：相同前 32 条 prompt/hash/reference 和 greedy 首 token 全部一致，但生成后续 token 会有数值敏感漂移。四个首批中，逐 token 完全一致仅 19–22/32；解析后选项相同为 29–32/32。也就是说，大多数差异发生在答案解释文本，但部分 MC 解析答案确实变化。该现象说明 GPU 批量 greedy 解码对微小浮点差异敏感，不能宣称重复生成逐 token 确定；这不是 fit/mapping 数据错配，也没有证据表明 full 评测 prompt 不同。

修复了验收定义：exact input row/reference/prompt hash 与首 token 仍必须一致；后续 token 的首分歧位置、全文一致数量和解析答案一致数量都保存为 parity 诊断，不再因自然语言续写尾部差异而丢弃完整评分。更新后的单元测试覆盖该行为。**首批解析答案一致率为 90.6%–100%，仍存在一个最高 3/32 的 smoke 答案差异**，因此正式比较需谨慎解释；paired bootstrap 只覆盖样本不确定性，不涵盖 GPU 数值/重复生成不确定性。smoke 从不加入分数。四个 ARC full 结果本身经过正式数据及输出审计，可以保留。

恢复队列已复用通过审计的 fit/validation 和 ARC full 结果，从 MMLU-Pro off 继续，避免重跑或覆盖已保存输出。进度跟踪见 `checks/resume_evaluation_process.json` 和 `status.py`。其他正式任务尚在进行，最终结果仍需 52/52 全部完成后出具。

## 8. 确定性解码修复：恢复严格验收并重跑正式评测

第 7 节的“放宽全文一致要求”不是最终采用的方案。继续追查后，新增了独立进程诊断，保留前 32 条 ARC 输入、全部 mapper、128-token 输出预算，并逐步保存 top-2 logits。默认 CUDA 路径两个新进程只有 18/32 条生成序列一致；分歧位置可观察到 BF16 候选 logits 在并列与相差一个量化步长之间变化。输入、权重相同不足以保证原运行环境的逐 token 可重复性。

启用 `CUBLAS_WORKSPACE_CONFIG=:4096:8`、`torch.use_deterministic_algorithms(True)` 后，两个独立进程使用不同随机种子（42、43），**32/32 条全部生成 token 一致，所有生成步骤的 top-2 logits 也完全一致**。证据位于 `checks/generation_diagnostic/`。这支持数值执行非确定性解释，但没有把根因限定到未经单独隔离的某一个 CUDA kernel。

最终处理：所有原正式/部分输出已整体移至 `runs_nondeterministic_v1/`，退出最终汇总；原失败与恢复日志保留在 `checks/nondeterministic_v1/`。从零重新运行 52 个正式评测单元，使用 `deterministic_eval.py` 设置确定性环境、固定 seed=42，并逐单元写入 `runtime.json`。正式审计必须验证该 runtime；smoke/full **全部保存记录必须完全一致**，不能只检查首 token。

原来通过完整方程残差和持出验证的 mapper 保留。没有改拟合公式、数据、权重、生成预算、prompt 或评分器；改变的是正式评测的 CUDA 执行设置。原 v2 审计冻结文件已恢复，不覆盖历史；新增 `configs/deterministic_evaluation_v3.json` 记录本次变更。全部 29 项测试通过。最终分数只来自这次确定性运行，先前 ARC 分数不得作为最终分数。

## 9. MC 评分格式漏识别修复

对已完成 MMLU-Pro 的 EOS 未解析输出抽查发现真正的评分缺陷：原 parser 不支持 `\\boxed{\\text{D}}`、`**F**. 解释` 等明确选项。不能把这些格式直接计成模型答错。新增独立 `rescore_mc.py`：只规范包住单个选项的 LaTeX 展示命令和 Markdown 粗体/代码标记，再应用原有选项解析优先级。parser 只接收预测文本与选项数量，绝不接收正确答案；对所有方向/方法和 off/on 一致使用，不能仅修正某一方法。41 项测试通过，包括格式正例、普通文章/多选项讨论/未闭合 thinking 等反例。

原冻结的 `evaluate.py`、每条生成 token、原始评分和审计证据均不改变。最终 report 从已审计输出重算 MC 分数，逐单元存储 `mc_scoring_v2.json`，包含旧分数、新分数和每条变更明细。`RESULTS.json` 保留 `scoring_v1`，最终主指标使用 v2。这是数据集评分纠错，不是训练或超参数调优。

因此之前口头报告的 MC 数字属于 parser v1 暂定分数，不是最终值。v2 下 ARC/off 为 0.6→1.7 weighted/readout 57.08%/58.45%，反向 66.04%/72.10%；MMLU/off 为 28.43%/30.57%，反向 23.71%/27.93%。Hotpot/RULER 不受该 MC 格式修复影响。后续正式单元仍采用相同 v2 评分。

## 10. 8k-token MC 与32k RULER 同卡内存冲突

2026-10-19 23:58，17_06 weighted MMLU-on 首批 smoke 在8192-token预算内继续解码时 OOM；同卡32k RULER 占用约41.4GiB，MC约52.9GiB，无法再分配1.05GiB。错误日志完整保留在 `checks/oom_schedule_v3/`。这不是数值错误，但说明两条任务队列不能无条件共用96GB卡。该失败 smoke 未进入正式结果，没有减少题目或截断预算来掩盖失败。

调度修复：所有 GPU 子任务获取文件锁，普通任务使用共享锁，ARC/MMLU reasoning-on（8192新token）使用独占锁。因此长MC同卡只运行一个任务，其余阶段仍可同时运行两条队列。停止旧协调器及其明确所属进程组后，从完整批次的预测记录恢复所有未完成任务；完成产物保留。批大小、生成预算、模型、mapper、随机种子、确定性设置及评分器不变。记录于 `configs/scheduling_amendment_v5.json`。
